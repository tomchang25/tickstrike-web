怎麼讀這張圖 這條鏈是單向的：core 同步改完 World 並吐出一串 CombatEvent（純資料），presentation 只讀那串事件加 snapshot 來演出，永遠不會回寫 core。所以追一個 bug 時先問自己：症狀是「數值/判定錯」（往 core 找）還是「畫面/動畫錯」（往 presentation 找）——兩邊用事件切開，很少需要同時看。

① 主流程：一次玩家攻擊 / 移動

這是 type: "attack" | "move" | "dash" | "smash" 這類會消耗一個 tick 的指令走的路。reward / milestone / cancel 走簡化版（見 ③）。

1 React 輸入

鍵盤 / 指標 → 產生 GameCommand

鍵盤與滑鼠事件在 hook 裡被翻成 move / attack / dash / smash callback。moveOrAttack 會先用 previewAttack 純讀 snapshot 決定這一步是打還是走。execute() 只是包一層 setBusy。

2 Runtime 佇列

execute() → submit() → drainCommands()

每個輸入包成一個 job 進佇列，序列化執行（一次只跑一個 turn）。submit 送出時會把上一回合還在跑的 VFX 快轉到結束（finishActive），所以連點不會被前一段動畫卡住。

3 Core 入口

resolveCommand()：守門 + 分派

先擋掉不該處理的狀態（encounter 已結束、有待選 reward、有待決 milestone），再跑 resolvePlayerAction。玩家這步被拒就直接回傳、不動 tick。被接受才進入完整回合結算。

4 Core 回合結算

finishAccepted()：一個 tick 的所有階段

玩家動作被接受後，這裡按固定順序跑完整個 tick，並把每個階段吐出的事件依序串成一條 completeEvents：
玩家事件 → advancePlayerAction → resolveEnemyPhaseSlots（敵人階段）→ resolveWavePhase（波次）→ updateEncounterOutcome（勝負）→ recordEvents → purgeTerminalEntities（移除這批打死的實體）。

5 Core 敵人階段

resolveEnemyPhaseSlots()：每個敵人一個 slot

逐一敵人跑：先處理 telegraph 收線與攻擊落地，再推進狀態（stagger / recover / rest），最後 ready 的敵人才 decideAtSlot 決策並 applyDecisionAtSlot 落地。role 專屬邏輯不寫在這裡——透過 getEnemyBehavior(role) 從 registry 取（見 ④）。這是「加一個敵人不用動 enemy-phase」的關鍵。

② 兩條播放路徑（為什麼有兩個 play）

這是最容易看糊的地方：同一批事件，runtime 會走其中一條，不會兩條都走。判斷點在 game-runtime.ts:330。

路徑何時走做什麼入口
turnOrder.play
分節奏		 resolution 帶 turnPlayback（一般消耗 tick 的指令） 按 actor 分組，一格一格演：玩家 slot → 每個敵人 slot → 收尾。格與格之間插入 handoff 停頓（fast 100ms / normal 250ms），同時更新上方回合條。 turn-order-controller.ts:171
presentation.play
一次全放		 沒有 turnPlayback 時的後備 把整批事件一次丟進 playNow，所有動畫並行跑完。 presentation-director.ts:120

兩條最後都落到同一個 PresentationDirector.playSlot / playNow 去產 GSAP timeline——差別只在「分幾次餵、要不要插停頓」。所以動畫本身怎麼演的 bug 一律看 presentation-director.ts；「節奏 / 回合條 / 停頓」的 bug 才看 turn-order-controller.ts。

③ 側向輸入（不走完整回合的三種）

reward 選卡、milestone 決定、smash 取消都經同一個佇列（submit）序列化，但都不跑敵人階段、不跑演出 timeline，只 emit() 發佈新 snapshot。這是它們比主流程短很多的原因。

④ Content 掛載點：加一個敵人動哪三個檔

整套 registry pattern 的用意就是：新增一個敵人 = 各加一個 module + 各加一行 registry，hub（enemy-phase / world / director）一行都不用改。代價是靜態追蹤會斷在 registry——真正的 dispatch 是 runtime 用字串 key 做的。

content 側		 src/content/enemies/features/<name>.ts features/index.ts:29 enemyFeatures 直接列在陣列
role 邏輯

追蹤斷點怎麼過 對 bombEnemyBehavior 按 Shift+F12 只會找到 registry 那一行，因為呼叫端是 runtime 拿字串 "bomb" 去查 Map。想找「誰真的觸發它」時，改搜字串 key（"bomb" / "enemy.bomb"），不要搜 function 名字。這是唯一一個 registry pattern 讓你多付的成本。

⑤ 為什麼 core 和 presentation 這樣切（Determinism 單向閥）

整條鏈是一個單向閥：

core 只寫 World、只吐事件；presentation 只讀事件、只碰畫面。事件流是唯一的縫。 core 同步跑完一個 tick（步驟 3–6），把發生的事寫成純資料 CombatEvent[]。presentation（步驟 7–9）只消費這串事件加 snapshot，永遠不回寫 core。這就是你當初為了 determinism 做的 logic / presentation 拆分——它的回報是：同一個 seed + 同一串輸入，core 一定跑出同一串事件，跟畫面演成怎樣完全無關。replayCommandLog（game-runtime.ts:232）就是靠這點重播整場。

實務推論：presentation 那層再怎麼改都不會弄壞遊戲性（有視覺 regression 擋著就夠）；但只要改動會影響 core 吐出的事件內容或順序，就是動到 determinism，需要 same-seed 事件序列比對，不能只看測試綠。這也是 CLAUDE.md model-tier 規則把這兩類分開的原因。

⑥ VS Code 導覽捷徑

「看到 function 名字卻不知道 define / caller 在哪」在這個 repo 是環境問題，不是 TypeScript 的宿命。用 VS Code 開這個資料夾、確認右下角 TS 語言伺服器有起來，以下開箱即用（import 進來的一樣能跳）：

快捷鍵作用什麼時候用
Ctrl + 點擊 / F12跳到定義順著呼叫往下鑽
Shift+F12Find All References（反查所有 caller）「誰在用這個」——但遇到 registry 會斷，改搜字串 key
Alt+F12Peek definition（不離開當前檔）只想瞄一眼型別/實作
Ctrl+T全 workspace 用名字搜 symbol不知道檔案在哪，只記得名字
Shift+Alt+HCall Hierarchy（呼叫樹）展開「誰呼叫它、它又呼叫誰」整棵樹
registry pattern 的追蹤限制 這個 codebase 大量用 role 字串 → 實作的 Map（enemy behavior、presenter、feature）。對這種 code，Shift+F12 和 Call Hierarchy 都會停在 registry 那行，因為真正的 dispatch 是 runtime 用字串做的、靜態分析看不到。對付它的通用招：改用 Grep 搜字串 key（例如 "bomb"），不要搜 function 名字。知道這條規則後，斷點從「惡夢」變成「多一次 grep」。
